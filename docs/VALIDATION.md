# 公式との比較手順

## 比較の意味

「同じ盤面と現在ブロックに同じ操作をしたとき、同じ結果になる」ことを基本とする。ただし、進行段階・過去最大値・時間状態が遷移に影響する場合は、それらも一致させる。

一致を判定する項目は、安定後の盤面、現在・予告ブロック、得点差、進行状態、入力の受理、終了状態。処理順を判別するケースでは途中の盤面とイベントも比較する。見た目だけが似ていても一致とはしない。

## 観察の準備

1. AndroidのアプリID、バージョン、モード、端末・OS、画面条件を記録する。
2. 初回チュートリアル中か通常プレイかを明記する。
3. ブースター・復活を使わず、操作前から解決後まで記録する。
4. 時間進行に関するケースは入力時刻、待機時間、停止時間も記録する。
5. 生成値は画面から記録し、内部の乱数や未表示の将来ブロックが分かるとは仮定しない。

原作では任意盤面を設定できるとは限らない。まず自然なプレイから判別可能な場面を採取し、その盤面をクローンの診断機能へ読み込む。狙った場面を得られなければ未確認と記録する。

動画の提供条件、フレーム抽出、読み取りの確かさ、仕様推定の限界は[プレイ動画の解析](VIDEO_ANALYSIS.md)を参照。OCR結果だけで期待結果を確定せず、該当フレームを確認する。

## 必須の比較ケース

以下は比較課題。[提供録画の観察記録](observations/README.md)の3場面について、転記した盤面・操作に対するクローンの結果を比較済み。対象版の固定と全条件の比較は未実施。「合体するはず」などの仮定で未観察の結果を埋めない。

| ケース | 場面・操作 | 観察する結果 |
| --- | --- | --- |
| V01 | 新規開始を複数回確認。通常モードと端末条件を記録 | 初期盤面、列・行容量、得点、予告、比較対象の固定 |
| V02 | 空列、異値の上、左右端の列に落とす。列境界も操作 | 着地位置、列判定、異値が残るか |
| V03 | 入力せず待つ。一時停止・再開も行う | 自動落下の有無、時間・既定列、停止中の挙動 |
| V04 | 同値の真上に1個落とす。複数の数字で確認 | 合体値、残る位置、得点差 |
| V05 | 下は異値、左だけ・右だけが着地点と同値 | 横方向の合体、左右対称性 |
| V06 | 斜めだけが同値。落下途中で同値の横を通る場面も採取 | 斜めでは合体しない（USER-0001）。移動中・上方向は連鎖中の場面で確認 |
| V07 | 着地ブロックを含め同値3個・4個が接する | 3個は4n（USER-0001）、4個は8n（OBS-0002）。対象範囲、残存ブロックと位置を比較 |
| V08 | 直接隣接の先にも同値が連なる形を採取 | 直接隣接と連結集合の区別 |
| V09 | 下と横が同値で、合体後の数字も別方向にある非対称の形 | 先に解決する方向、同時処理か逐次処理か |
| V10 | 合体でブロックが消え、その上に別ブロックがある | 重力、空洞の有無、落下順 |
| V11 | 合体結果が別の同値に接する。既存ブロックの落下で別の合体も起こる | 連鎖の対象・範囲・終了、解決順 |
| V12 | 上端直前の異値列に置く。一列だけ満杯と全列満杯を区別 | 上端の容量、入力拒否とゲームオーバーの違い |
| V13 | 最上段で同値を合体させる。満杯列への追加投入は別条件で確認 | 最上段の合体救済と合体後の終了判定（USER-0001）。連鎖・重力を解決する範囲も比較 |
| V14 | 落下・連鎖中に連打。置けない場所や盤面外も操作 | 入力予約、受理回数、予告・手数・乱数の消費 |
| V15 | 高い数字の初到達と再合体。小さい数字を複数位置に置いた場面を採取 | 閾値、消去対象、既存最小値との関係、消去後の重力・連鎖・得点 |
| V16 | 序盤と履歴最大値16・128・256以上で生成列を採取 | 上限8・64・128（USER-0001）、初期候補と下限、均等分布の仮説を比較 |
| V17 | 履歴最大値更新・消去の前後で現在・次ブロックを追う。盤面最大と履歴最大が異なる場面も採取 | 履歴最大値による上限と予告更新の順、候補外予告の扱い |
| V18 | 合体なし、2個合体、複数合体、複数段連鎖、連続した手での合体 | 得点式、ボーナス、リセット条件 |
| V19 | 大きな数字まで進め、到達時の表示と継続を確認 | 約400万までの到達報告（USER-0001）と、それより先の上限未確認を区別 |
| V20 | 一時停止、終了、再起動から再開する | 盤面・得点・予告・進行状態・時間状態の復元 |

## 記録から検証用データへ

- [観察テンプレート](observations/TEMPLATE.md)を複製し、1ケース1記録で保存する。
- 盤面は画面の上から下、各行は左から右へ記録する。空マスは `0`、数字は表示値のまま記載する。
- 観察時の列は左から `1` と数える。エンジンAPIは0始まりとし、変換を明示する。
- 落下中のブロックを安定盤面へ混ぜない。途中状態は別に記録する。
- 得点は操作前後の値と差を記録する。生成列とタイムスタンプも必要な範囲で記録する。
- 期待結果は公式の記録から手動で作る。クローン自身の出力を期待結果の根拠にしない。
- データには観察ID、比較対象版、ルール設定版、影響する進行状態を付ける。

`tests/fixtures/official/` に動画観察3件のfixtureを保存済み。比較対象は観察した配置・安定後の盤面・得点・合体値・終了状態に限定する。seedや将来の生成値は観察値ではなく試作設定。ユーザー確認に基づく3個合体・最上段救済の合成例は `tests/fixtures/reported/` で区別する。未観察の例を公式データとして追加しない。

## 判定と修正

各ケースを `未観察 / 記録不足 / 一致 / 不一致 / 対象外` で管理する。複数条件が必要なケースは条件別に分ける。1回の観察で未知のすべての境界条件が確定したとは扱わない。

不一致は、記録の転記、入力・時間条件、ルール設定、実装の順に確認する。修正時は期待結果の根拠を保持し、公式との比較とクローン内の再現性検証を再実行する。

## ブラウザー版と学習用エンジンの比較

同じPythonエンジンでも、CPythonとブラウザー内のPyodide、転送処理、入力イベントに差が入る可能性がある。共通の公式由来データを両方で実行し、盤面・得点・進行・終了・解決イベントを比較する。

この実行環境間の一致は公式との一致とは別の検証。`npm run test:parity` では5件の初期状態と操作をCPython・Node.js上のPyodideで実行し、状態・イベント・乱数を含む出力全体を比較する。実際のブラウザーでは別途、Worker経由の操作・表示・保存・読み込みを確認する。合成したデータを「公式」と呼ばない。

時間進行は自然落下オンで同じ入力・時間列を与えて比較し、画面のフレームレートと区別する。自然落下オフとAIはターン制として、同じ状態・操作・生成列で安定後の結果を比較する。待機で状態・乱数が進まないこと、切替で過去の待機時間が投入されないことも確認する。得点の補間表示は計算結果と区別し、演出後の値を比較する。大きな数字と得点は文字列転送で欠落しないことも確認する。公開URLの操作確認は[公開手順](DEPLOYMENT.md)を参照。

## 生成分布の比較

固定した生成列を使う検証は、盤面遷移の一致だけを示す。生成アルゴリズムの一致とは区別する。

生成分布は対象バージョンと進行段階をそろえて調べる。各段階でまず1,000個を収集目標とし、実数・候補値・度数・割合・収集セッションを残す。これは初期の調査目標であり、十分な精度や一致を保証する数ではない。

候補集合は「観察した集合」と「出現しうる全体」を区別する。未出現の値を確率0と断定しない。頻度の不確かさ、連続出現、直前値や盤面との関係も確認する。

比較レポートには採用する推定分布、その根拠、不確かさ、追加収集が必要な点を記載する。原作の内部乱数seedが不明なため、生成列そのものの完全一致は要求しない。第一段階の完了判定では、この統計的な推定と確定的な遷移の一致を別々に報告する。

## 比較完了時のレポート

対象版・モード、使用した観察ID、ケース別判定、確定したルール、残る推定と未確認、対象外の機能を一覧にする。同一性の主張は確認した範囲に限定する。完了条件は[開発計画](ROADMAP.md)を参照。
